# MIRVIX AI — аудит архитектуры и необходимых доступов
Дата: 12 ноября 2026 · Основание: репозиторий `chistocrym-wq/mirvix-ai`, ветка PR №36 `feature/geo-publisher-mvp`, рабочая ветка `feature/intelligence-evidence-source-repair-20261112`.

## Критерии оценки

- **Есть в коде** — функция/обработчик существует. Это не доказывает, что внешний API доступен, оплачен и проходит живой запрос.
- **Проверен тестом** — локальные unit-тесты GitHub CI; не равнозначно проверке внешнего сервиса.
- **Подключено** — этот статус можно установить **только** после просмотра конфигурации Netlify/внешнего провайдера и удачного ограниченного реального вызова.
- **Нет данных** — не показывать в клиентском отчёте как ноль, отсутствие бренда или подтверждённое преимущество конкурента.

| GEO Publisher | ТЗ, таблица площадок, ручная проверка условий и экспорт | Нет автоматических подтверждений публикации/цен и доказанной атрибуции GEO-эффекта |

**Обнаруженный и исправленный дефект PR №36:** SEO-отчёт брал `run.platforms[].matches`, однако `collectPlatforms` исключает сайт клиента и заданных конкурентов. Следствие — неверная/неполная сравнительная таблица. Теперь для SEO используется исходная полная выдача `run.searchHits`, а `run.platforms` остаётся фильтрованным списком GEO-площадок. Для старых ответов API без `searchHits` интерфейс требует повторного получения данных вместо демонстрации ошибочной аналитики.

## Технические блокеры до коммерческого запуска

1. Оценить подключённость и **живым ограниченным запросом** подтвердить каждый API, логируя только HTTP-код, тип ошибки, стоимость и источник, **без секретов и чувствительных ответов**.
2. Спроектировать изоляцию клиентов в Supabase: организации, пользователи, роли, проекты, кластеры, подтверждённые/возможные конкуренты, SERP-замеры, AI-ответы, цитирования, затраты, отчёты, планы работ. RLS и тест «клиент А не видит клиента Б».
3. Добавить серверные ограничения бюджета и выполнение в очереди с возобновлением; не полагаться на открытую вкладку.
4. Разработать обратную семантику: сравнить провайдеров по реальному покрытию и тарифам.
5. Подключить согласованные аналитические аккаунты через безопасный OAuth, а не запрашивать пароли в чате.
6. Отделить SEO-готовность, техническую GEO-готовность, частоту упоминаний и долю цитирования; каждую метрику показывать с источником, периодом и выборкой.
7. Провести реальные проверки на многоуслужной клинике, магазине, локальном сервисе и сайтах с недоступным API/аналитикой; отдельно проверить мобильную версию, экспорт и роли.
