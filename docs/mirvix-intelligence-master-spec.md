# MIRVIX AI Intelligence — единое техническое задание и дорожная карта

## Цель
Построить клиентскую систему, которая объясняет на основании источников: (1) готов ли сайт к индексированию, поиску и цитированию; (2) по каким коммерческим запросам клиент уступает реальным конкурентам; (3) где клиент и конкуренты появляются в ответах доступных ИИ-API; (4) откуда приходят визиты и **заявки**, если клиент дал доступ к аналитике; (5) что конкретно исправить, чтобы увеличить релевантное присутствие и обращения.

Целевой пример: многопрофильная клиника с отдельными направлениями МРТ, КТ, кардиологии, УЗИ, гинекологии, стоматологии и т.д. Нельзя считать, что клиника предоставляет услугу, без подтверждения на сайте. Медицинские рекомендации для пациентов не генерируем, оцениваем только маркетинговые источники и организационную видимость.

## Этап 0. Ввод
Обязательно: сайт, название, география, согласие владельца на проверку. Опционально: известные конкуренты, направления, бизнес-цели и доступ к GSC, Яндекс.Вебмастеру, Метрике, GA4, CRM. Каждой клиентской организации — собственный набор запусков, ролей и доступов, разделение доступа на уровне БД.

## Блок 1. Технический аудит
Повторно использовать site-audit.mjs. Проверять HTTPS, индексируемость, robots, sitemap, canonical, title/H1, структуру услуг, техническую мобильность, доступность HTML, Organization/MedicalClinic/Physician JSON-LD, реальные контакты, локальные карточки и врачей, структурированную информацию об услугах, вопросы-ответы, скорость/Core Web Vitals при наличии отдельного измерения. Отдельно считать обнаружение robots-запретов для поисковых/ИИ-ботов. Ошибка получения сайта не равна «плохой сайт». llms.txt — необязательная экспериментальная подсказка, не фактор гарантированного ранжирования. На уровне каждой услуги — наличие собственной посадочной и доказательств доверия.

## Блок 2. Поисковая аналитика
Собирать запросы из:
- Google Search Console Search Analytics API (только при предоставленном владельцем доступе), реальная история показов, кликов, CTR и средней позиции;
- Яндекс.Вебмастера (доступ владельца), фактические запросы и позиции в доступных разрезах;
- санкционированного SERP API Google и Яндекса: независимая выборка топ-20 по региону и запросу;
- вручную добавленных коммерческих запросов и кластеров.
Нельзя подменять GSC наблюдаемым top-20. Нужно показывать отдельно «позиция SERP на дату запроса» и «средняя позиция GSC за период». Выделять брендовые и небрендовые запросы, услуги и геомодификаторы, группы и сезонность. Кластеры должны включать разные интенты: выбор клиники, запись, цена, врач, диагностика, сравнение, срочность (без утверждения о медицинских показаниях).

## Блок 3. Автоматическое выявление конкурентов и обратная матрица
1. Найти домены, регулярно встречающиеся в выдаче по выбранным кластерам.
2. Классифицировать домены: прямой конкурент, каталог/агрегатор, СМИ/площадка, справочник, нерелевантный сайт. Автоматическое определение — гипотеза до проверки.
3. Для подтверждённых прямых конкурентов собрать их видимость по дополнительным запросам из разрешённого источника keyword gap / reverse rank dataset. Нельзя утверждать, что top-20 по исходным запросам раскрывает **все** запросы конкурентов.
4. Добавить конкурентную матрицу услуга × регион × запрос × источник × позиция × дата × клиент/конкурент.
5. Пример «МРТ в СПб»: сервис наблюдает «Клиника Б» на позиции 2; клиент отсутствует в наблюдаемом топ-20. Предложить точную посадочную, FAQ, карточку компании, источники доверия и приоритетный GEO-материал.
6. Отдельно классифицировать возможный конкурентный бренд и источник цитирования — это принципиально разные сущности.
7. Для подтверждения конкурента нужно название организации, домен, обоснование, дата, источник; специалист может подтвердить/отклонить кандидатуру.

## Блок 4. Матрица запросов ИИ
Запросы не должны генерироваться произвольно. Первичный набор: (A) наблюдаемые коммерческие запросы, на которых опережают конкуренты, (B) поисковые данные владельца, (C) запросы из зафиксированных результатов ИИ-конкурентов. ИИ преобразует их в естественные вопросы пользователей: «Посоветуй, где пройти МРТ в Петербурге», «Где записаться к кардиологу с хорошими отзывами?», и сохраняет связь исходный факт → новый вопрос.
После проверки появляются новые направления, основанные на ответах/цитатах конкурентов, и проходят ручную валидацию.
Поддерживать несколько уровней глубины, ограниченный бюджет, повторяемость набора и даты, версию модели, источники, сбои, стоимость вызова.
Подключения: ChatGPT API, Gemini API, Perplexity API, Grok API, DeepSeek API, GigaChat API, Yandex Alice AI Studio API. Состояния — ключ не подключён / API ошибка / ответ без веб-поиска / веб-поиск выполнен / достоверность не установлена. Никаких обещаний, что ответы этих API совпадают с тем, что пользователи видят в приложениях. Нельзя считать ошибку API или ответ model-only нулём присутствия.
Из каждого ответа извлекать: названные компании, имена и домены, контекст рекомендации, источники/цитирования, позицию упоминания *внутри ответа*, наличие собственного бренда и конкурентов, вероятность ложного совпадения. Новые имена конкурентов — кандидатуры на верификацию специалистом, не автоматический факт.
Результат: heatmap запрос × провайдер, подтверждённое упоминание, ссылка на источник, тематический разрыв и план действий. Для сопоставимости — одинаковые вопросы, период, регион и методика.

## Блок 5. Клиентский трафик и заявки
Интегрировать Яндекс.Метрику и Google Analytics 4, желательно напрямую через API по согласованному OAuth/токену с read-only scope. Обязательные показатели за период: визиты, посетители, канал, UTM, переходы с ИИ-доменов, конверсии/достижения целей, звонки, формы, записи. CRM используется для регистрации квалифицированного лида, заказов и оплаты. Не объединять визиты и продажи или оценку SEО-эффекта без согласованных целей и атрибуции. ИИ-рефереры могут быть скрыты; отсутствие referrer не доказывает отсутствия посетителя.
Если нет доступа, показывать «нет данных» и предлагать ручную выгрузку с явной пометкой. Не собирать персональные или медицинские данные пациентов: только агрегированные показатели.

## Блок 6. Конкурентные возможности
Система предлагает приоритетный список задач по ожидаемой сложности, стоимости и подтверждённому разрыву: исправить noindex / индексирование, обеспечить полноту карточек организации, структурировать услуги и посадочные, добавить авторские материалы с проверяемыми ссылками, повысить достоверность бренда, разместить редакционные публикации на релевантных внешних ресурсах, улучшить ответы на запросы с отсутствием бренда, устранить SEO-разрыв по ключевым услугам. Не предлагать поддельные отзывы, искусственные цитирования, фиктивные публикации или скрытое вмешательство в чужие сайты.
Связать с GEO Publisher: список проверяемых сторонних площадок → условия публикации → согласованный материал → реальный URL публикации → последующие наблюдения AI-цитирования. Совпадение по времени не доказывает причинность.

## Клиентский интерфейс
Один читабельный отчёт: 1) обзор и источник данных; 2) техническая готовность; 3) SEO Google и Яндекс; 4) выявленные конкуренты; 5) heatmap ИИ; 6) визиты/лиды/атрибуция; 7) конкурентные разрывы и план; 8) бюджетный план 30/60/90 дней; 9) документированная динамика до/после.
Тёмная брендовая консоль для специалиста, светлая или печатная версия для клиента, мобильный responsive. Каждый показатель с источником, статусом, периодом, охватом. Пустые данные — честный «не подключено».

## Состояние реализации (12 ноября 2026)
Уже существующие рабочие компоненты: site-audit; geo-prompts; direct-geo (7 сервисов, часть ключей может отсутствовать или API может не отвечать); geo-publisher (тестовая ветка, отдельный PR).
**Реализовано в ветке PR №36**: новая /intelligence/ с загрузкой SEO-истории GEO Publisher, разграничением компаний-кандидатов и каталогов, матрицей запросов на основе реально наблюдаемой выдачи, вызовами выбранных настроенных ИИ, выводом ответов и источников, обработкой ошибок, техническим аудитом, импортом агрегированного CSV (визиты/лиды), списком приоритетных действий, клиентским печатным отчётом и JSON-выгрузкой. Выборка не является обратным полным исследованием ключей конкурентов. AI-результаты текущей страницы сохраняются только в открытой вкладке.
**Не реализовано**: полноценная обратная keyword-gap разведка; автоматическое извлечение названий компаний из всех ответов с верификацией; автоматические OAuth-подключения GSC, Яндекс.Вебмастера, GA4, Яндекс.Метрики и CRM; независимые серверные очереди с квотами; защищённое долговременное хранение измерений AI по клиентам и ролям; генерация отдельных прогнозов и причинных выводов. До коммерческого запуска требуется завершить эти пункты и провести пилот с разрешениями и лимитами.

## Приёмка
1. При техническом недоступном сайте показывать ошибку/неизвестно; не проставлять ноль.
2. SERP по фиксированному запросу и региону сохраняет URL/позицию/дата/система; 100% выводов позиции подтверждены данным источником.
3. Нельзя записать каталог или информационную статью как прямого конкурента без проверки.
4. В матрицу ИИ попадают вопросы с происхождением от исходных наблюдаемых кластеров. Случайные вопросы отдельно маркируются гипотезами.
5. Все ИИ-ошибки и model-only ответы исключаются из знаменателя search-grounded видимости.
6. Нет трафика без подключённой аналитики/выписки, нет лидов без связанной CRM или подтверждённой таблицы.
7. Ссылки на источники, даты, покрытия и погрешности видны в отчёте.
8. Контролируемый пилот на 5–10 сайтах в различных направлениях, оценка конкурентной релевантности и повторяемости.
9. Не раскрывать API-ключи клиенту; HTTPS, авторизация сотрудников и разграничение доступа.
10. Главный production MIRVIX не менять до проверки Preview и подтверждения владельца.
